**Architecture Review**

**Engineering Architecture Blueprint v1.1 — Digital Billing Core**

Production-grade review · millions of merchants, India scale

Method: Architecture Review skill (severity-ordered; invariants first; changes require strong justification)

Verdict: architecture sound in shape; 2 blocking findings, 3 failure-map gaps, 2 ops findings, 2 cost items, 2 nits

Load-Bearing Numbers: Status

Stated in Blueprint §1: 50k TPS design ceiling / T1 500-peak deployment; ACK \< 200 ms; generation p95 \< 2 s; 99.9% generation availability; idempotency and metering as never-wrong invariants; 90-day PII scrub; strict tenancy. Sufficient to review against. Still MISSING (carried, unowned): ratified peak-TPS target; PG hash spec and retry schedule; PG settlement-extract availability (newly surfaced by finding F-5). No opinion below relies on a missing number; two findings exist precisely because a stated number (the 50k ceiling, the 200 ms ACK) is contradicted by the design as written.

\[BLOCKING\] Findings

F-1 · The v1.1 contact_ref fix put PostgreSQL on the 50k-TPS synchronous path

|                |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
|----------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Problem        | v1.1 fixed “PII in Kafka” by having Ingestion write the contact to the PII Vault (Postgres) synchronously before ACK, and Dispatch read it back per send. That places a relational database on both hot paths. It also creates a non-atomic dual write on the ACK path (Vault insert + Bill Store conditional put): a crash between them orphans PII or produces a bill with a dangling contact_ref — no failure story exists for that state.                                                                                                                                                                                                                                                                  |
| Impact         | The 50k ceiling claim is false as written — single-writer Postgres saturates orders of magnitude below the ceiling, so the Vault becomes the exact bottleneck the KV Bill Store was chosen to eliminate. Worse, availability coupling: Vault down = ACK path down, violating the blueprint's own headline property that the ACK path survives downstream outages. The v1.0 inconsistency was real, but the v1.1 cure moved the problem somewhere more expensive.                                                                                                                                                                                                                                               |
| Recommendation | One write on the hot path. The contact travels inside the bill record as a field-level-encrypted blob under the PII KMS key: Ingestion does a single conditional put (KV — scales linearly, atomic with idempotency). Events carry bill_id only; Dispatch does a KV point read (scales); the CRM consumer copies the contact into the Vault asynchronously (Vault load becomes eventually-right class, tolerant of lag). The 90-day scrub nulls the encrypted field and deletes the Vault rows — same targeted-delete property, and crypto-shred still works because the field key is the PII key. “PII never rides Kafka” is preserved; “PII only in stores under the PII key” becomes the sharper invariant. |

F-2 · Dual write (Bill Store + Kafka publish) can silently lose bills

|                |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
|----------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Problem        | Ingestion conditionally puts the bill record, then publishes bill.requested. These are two systems with no transaction between them. If the process dies after the put and before the publish, the bill exists but no event ever fires: never rendered, never delivered, invisible to the merchant — and the idempotent conditional put means the PG's retry is absorbed without re-emitting the event. The blueprint has an outbox, but only as a DR fallback for Kafka outages (§15), not as the correctness mechanism for this everyday crash window. |
| Impact         | Low-frequency, silent, invariant-grade: a paid transaction with no bill, undetectable until a customer complains. At scale, “rare” per-request becomes daily in absolute terms. This is the textbook dual-write bug, and it violates methodology Card 5 (if you can't replay it, it isn't done).                                                                                                                                                                                                                                                         |
| Recommendation | Make the store the source of truth and derive the event: publish bill.requested from the Bill Store's change stream (CDC — DynamoDB Streams-class, or the outbox pattern promoted from DR fallback to the primary path). The conditional put then atomically both creates the bill and guarantees eventual event emission; the crash window disappears structurally rather than statistically. The reconciliation job (bills vs events) remains as the tripwire, but stops being the only line of defence.                                               |

\[FAILURE-MAP\] Findings

F-3 · Cross-region failover can mint two different bills for one transaction

|                |                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
|----------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Problem        | DR is async replication with LWW-class global tables. During a failover window, a PG retry lands in region B before region A's write replicates. The conditional put in B succeeds (key not yet visible), creating a second bill — and if bill_id is minted randomly per generation, the two records do not converge when replication merges: two bills, two URLs, possibly two sends for one payment.                                                                   |
| Impact         | Direct violation of the no-duplicate-bill invariant (FSD BR-1) in exactly the scenario DR exists for. Duplicate premium sends also corrupt metering.                                                                                                                                                                                                                                                                                                                     |
| Recommendation | Make identity deterministic: bill_id derived from the idempotency key (e.g., a keyed hash of merchantTxnNo+paymentID), so cross-region duplicates converge to one record under LWW instead of coexisting. The public URL hash stays random but is stored on the record — whichever write survives, one URL survives. Dispatch dedup keys on the idempotency key rather than a per-region bill_id. Cheap change now; near-impossible retrofit after URLs are in the wild. |

F-4 · Backups retain scrubbed PII past 90 days

|                |                                                                                                                                                                                                                                                                                                                                                                                                                   |
|----------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Problem        | The 90-day scrub nulls PII in live stores, but PITR (35 days stated) and snapshots of the Vault and Bill Store contain the pre-scrub bytes. A bill scrubbed on day 90 survives in backups until day 90 + retention — the blueprint never reconciles backup retention with the DPDP obligation.                                                                                                                    |
| Impact         | The scrub SLO (“100% by T-90+1d”, §14) is unmeetable as stated for the totality of stored data; a DPDP audit or deletion request could not be honoured from backup media.                                                                                                                                                                                                                                         |
| Recommendation | Policy, not re-architecture: (a) PII-store backup retention capped so backup age + 90 ≤ the ratified compliance ceiling, or (b) periodic PII-key rotation with old-key destruction, making aged backups cryptographically unreadable (the Vault's dedicated KMS key was chosen for exactly this — extend the same key to the encrypted contact field from F-1). Confirm the ceiling with Legal; record as an ADR. |

F-5 · The bills-vs-PG reconciliation assumes a feed nobody has confirmed

|                |                                                                                                                                                                                                                                                                                                                             |
|----------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Problem        | §14.2's daily “bills vs PG” job reconciles against “the PG transaction extract” — an artifact whose existence, format, and delivery cadence were never established. It joined the blueprint as an unflagged assumption.                                                                                                     |
| Impact         | If the extract does not exist or arrives weekly, the platform's defence against silently lost bills (see F-2) is weaker than the document claims, and the review checklist's “reconciliation live before first paying merchant” gate cannot be met.                                                                         |
| Recommendation | No design change — an ownership change: add the extract (or a query API on PG records) to the PG-team dependency list alongside the hash spec, with format and cadence agreed before build. Until confirmed, the internal-consistency job (bills vs event stream) is the operative tripwire and should be labelled as such. |

\[COMPLEXITY / OPERATIONS\] Findings

F-6 · Ingestion shares a deployable with the dashboard BFF

|                |                                                                                                                                                                                                                                                                                               |
|----------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Problem        | The Tier-1 physical-3 packaging bundles Ingestion (highest SLO, lowest change rate, machine traffic) with the BFF and Config (lowest SLO, highest change rate, human traffic). Every dashboard iteration redeploys the ACK path.                                                              |
| Impact         | The component with the strictest availability target inherits the deploy risk of the component that changes most — an SLO/churn mismatch. Canary gates reduce but do not remove it; a bad BFF dependency bump can still take the ACK path down with it.                                       |
| Recommendation | Four deployables, not three: Ingestion alone; (BFF + Config); async workers; analytics consumers. This is the one place monolith-first loses to isolation on strong grounds — the justification is the mismatch itself, not microservice fashion. Everything else about the packaging stands. |

F-7 · Engagement beacons route through the dashboard BFF

|                |                                                                                                                                                                                                                                                                                                                    |
|----------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Problem        | Bill-microsite open/click/widget events POST to the BFF — the same service serving merchant dashboards. Beacon traffic scales with bill opens (the largest request class in the system) while dashboard traffic scales with merchants logged in; one service, two unrelated load profiles.                         |
| Impact         | A viral-merchant open spike degrades every merchant's dashboard; capacity planning for the BFF becomes guesswork; a beacon-path bug and a dashboard bug share a blast radius for no reason.                                                                                                                        |
| Recommendation | A thin collector: gateway route → stateless beacon endpoint → Kafka engagement.events. A few hundred lines, no reads, trivially horizontally scalable, deployed with the analytics group. The BFF keeps only the interactive widget APIs (survey submit with once-per-customer check), which genuinely need logic. |

Decisions Challenged and Upheld

Per the brief, every major decision was attacked. These survived on their merits — recorded so the review is evidence the design was tested, not rubber-stamped.

| **Decision**                        | **Challenge Run**                                                                 | **Why It Stands**                                                                                                                                                                                                                     |
|-------------------------------------|-----------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Kafka as backbone (ADR-4)           | Is this the premature-distribution failure mode at 13-TPS market reality?         | Replay is load-bearing for F-2's CDC fix and for reprocessing; per-merchant ordering and 4+ consumers are named requirements; ADR-4 already carries its own revisit trigger. Token stays spent                                        |
| KV Bill Store over Postgres (ADR-3) | Could partitioned Postgres serve realistic (non-ceiling) volumes and cut a store? | Yes at T1–T2 — but the conditional-put idempotency and F-3's deterministic-identity fix lean on KV semantics, and a later Postgres→KV migration of the system's largest table is the worst possible re-platform. Ceiling justifies it |
| Async event core / 202 ACK (ADR-1)  | Does eventual visibility (~1–2 s) harm POS UX?                                    | Status endpoint covers it; the alternative (sync render) couples ACK latency to Chromium and provider health — strictly worse                                                                                                         |
| Static CDN bills + lazy PDF (ADR-5) | Re-render cost for scrub/credit-note versioning?                                  | Bounded, batch, off-peak; the availability property (bills viewable during total backend outage) is worth it                                                                                                                          |
| Warm-standby async DR (ADR-8)       | Is RPO ≤ 5 min acceptable for a billing system?                                   | With F-3 fixed, the replay window is safe (deterministic convergence); sync replication would tax every write for a rare event. Stands, contingent on F-3                                                                             |
| OAuth2 over API keys (ADR-7)        | Integration friction for small POS vendors?                                       | Friction is real but bounded (SDK + refresh tokens); unscoped unexpiring keys across millions of merchants is how tenancy breaches happen. Stands                                                                                     |
| Cell sharding deferred to T4        | Should cells arrive earlier for blast-radius?                                     | Cells double every operational surface; below 20k TPS the AZ+partition isolation already bounds radius. Earlier cells = complexity without a number demanding it                                                                      |
